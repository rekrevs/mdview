# T-0020: Render GitHub alerts and footnotes

**Status**: DONE | **Size**: M
**Phase**: -

## Context

GitHub renders `> [!NOTE|TIP|IMPORTANT|WARNING|CAUTION]` alerts and `[^n]` footnotes; mdview shows them as plain quotes/text. Part of the best-in-class parity work (2026-11-03 comparison with SharePoint/OneDrive and GitHub).

## Acceptance Criteria

- [x] All five GitHub alert types render with title, icon and colour in light and dark mode
- [x] Footnote references link to definitions and back-links return; numbering matches GitHub
- [x] Copy, find and outline keep working across alerts and footnotes
- [x] Renderer regression tests and GUI evidence; README and vendored licenses/manifest updated if a plugin is vendored

## Approach

Planned 2026-11-03 (Plan agent, Opus 5.5 xhigh).

- Step 0: record GitHub golden output with `gh api /markdown -f mode=gfm` for edge cases (lowercase marker, marker+text on one line, empty alert, alert in list/nested quote, repeated ref, label case, unused definition); tests follow the fixtures.
- Footnotes: vendor `markdown-it-footnote` 4.0.0 (MIT, archive sha256 319e1c78…e272) via vendor-renderer.py; disable `footnote_inline`. Override renderers to GitHub/cmark-gfm markup: `sup.footnote-ref > a#fnref-<label>[-N]`, `section.footnotes[data-footnotes]` with `h2#footnote-label.sr-only`, `li#fn-<label>`, `a.footnote-backref` `↩︎` (+`<sup>N</sup>`). Known deviations: case-sensitive labels, last duplicate definition wins.
- `reader_metadata` must run after `footnote_tail`; reserve footnote ids in the slug set. `scrollToHeading` tries raw, decoded and `user-content-`-stripped ids.
- Alerts: in-house core rule after `block`: top-level blockquote whose first paragraph's first line is exactly `[!NOTE|TIP|IMPORTANT|WARNING|CAUTION]` (case-insensitive) → `div.markdown-alert.markdown-alert-<type>` with `p.markdown-alert-title` + inline octicon SVG (aria-hidden). Octicon paths from `@primer/octicons` 19.42.0 (MIT), source SVGs + license vendored for provenance.
- Copy: drop `.octicon`, `.footnote-backref`, `.sr-only`; refs copy as `[n]`, footnote items `[n] `; portable alert/footnote styles in rich HTML. Find skips `.sr-only`.
- CSS: GitHub alert colours light/dark as variables; footnotes section small/muted with top border.
- Tests: renderer cases for all types/negatives/nesting/math, numbering, ids, clicks, copy, find, icon provenance; GUI checks for colours in light/dark, click ref ↔ back-link scroll, native copy, find, outline.

## Log

2026-11-03 (implementation agent, Opus 5.5).

- **Golden output.** `gh` was installed but its keyring token was invalid, so the fixtures came from the same endpoint without authentication: `POST https://api.github.com/markdown` with `{"mode":"gfm"}` (21 cases). Results, which the tests follow:
  - Alerts: `[!note]` (lowercase) and `[!NOTE]   ` (trailing spaces) are alerts. `[!NOTE] text` on the marker line, `[!INFO]`, the marker on the second line, a nested quote (`> > [!NOTE]`), a quote inside a list item and `> # [!NOTE]` all stay ordinary blockquotes.
  - A marker with no content (`> [!NOTE]`, or `> [!NOTE]` followed by `>`) stays an **ordinary quote**. A marker followed by a blank quote line and a paragraph is an alert.
  - **Deviation from the plan, following GitHub:** the escaped `> \[!NOTE]` is an alert on GitHub (`<div class="markdown-alert markdown-alert-note">…<p>x</p>`), so it is not a negative case. A lazy continuation line (`> [!NOTE]\nlazy`) becomes the alert's content.
  - Footnotes: `A[^b] B[^a] C[^b]` gives refs 1, 2, 1; ids `user-content-fnref-b`, `-fnref-a`, `-fnref-b-2`; `<li id="user-content-fn-b">` comes first. The back-links are `↩` and `↩<sup>2</sup>`, with aria-labels "Back to reference 1" and "Back to reference 1-2". An unused definition is omitted. Markup is `<section data-footnotes class="footnotes"><h2 id="footnote-label" class="sr-only">Footnotes</h2><ol>`, with no `<hr>`.
  - **Labels are case-insensitive** (`X[^Note] Y[^note]` with `[^note]:` gives refs 1 and 1 and one note). For duplicate definitions, **the first wins** (`[^a]: one` / `[^a]: two` shows "one"). Because of this, the plan's two expected deviations (case-sensitive labels, last duplicate wins) were not accepted; both now match GitHub (see the implementation notes below).
  - `[^missing]` and `^[inline]` stay literal. `[^ä]` has href `#user-content-fn-%C3%A4`. `[^my label]:` (with a space) is a link reference definition, not a footnote; markdown-it behaves the same.
  - GitHub appends a per-document hash to footnote ids (`…-3a373bd9…`) and adds the `user-content-` prefix. mdview uses the bare `fn-x`/`fnref-x` ids. `scrollToHeading` strips `user-content-`, but cannot map the hash suffix.
- **Tests first.** I added 13 renderer tests and put `vendor/markdown-it-footnote.min.js` in the harness load list. Before vendoring, all 35 failed (ENOENT). After vendoring, with the renderer unchanged, 11 of the 13 new tests failed (red evidence below). The two that passed are guards (the non-alert negatives, and "find ignores Footnotes") that hold vacuously without the feature.
- **Vendoring.** `scripts/vendor-renderer.py` now includes `markdown-it-footnote` 4.0.0 (MIT; tarball sha256 `319e1c78…2e272`, matching the plan; browser build `dist/markdown-it-footnote.min.js`, global `markdownitFootnote`). It also includes `@primer/octicons` 19.42.0 (MIT; sha256 `8ae65252de0d8b24e068362c375533ef9a00fdf04e99f23d80df680d34138237`; published 2026-10-23). From octicons, only `build/svg/{info,light-bulb,report,alert,stop}-16.svg` go into `vendor/octicons/`, plus `licenses/octicons.txt`. The note path matches the `octicon-info` path in GitHub's own alert output. A direct registry download failed with `IncompleteRead`, so I fetched the archives with `curl --retry` and ran the script in local-archive mode. `git diff --stat Sources/Resources/Web/vendor` shows only `manifest.json` (+26 lines); every existing vendored file is byte-identical, and the existing checksums were re-verified by the script.
- **Implementation (`renderer.js`).**
  - Alerts: a `github_alerts` core rule runs after `block`. It acts on a level-0 `blockquote_open` whose first paragraph's raw `inline.content` matches `^\\?\[!(note|tip|important|warning|caution)\][ \t]*(\n|$)` (case-insensitive). Editing `inline.content` is enough, because inline parsing runs later. The rule strips the marker line, or removes the paragraph when the marker is all it contains. If nothing follows the marker, the quote stays ordinary. Otherwise the quote becomes `alert_open`/`alert_close` (`div.markdown-alert.markdown-alert-<type>`) with an `alert_title` token that renders `p.markdown-alert-title` containing the inline `svg.octicon` (`aria-hidden`, `focusable="false"`). The icon paths were generated from the vendored SVGs, and a renderer test checks that they stay equal.
  - Footnotes: `md.use(markdownitFootnote)` with `footnote_inline` disabled.
    - Case-insensitive labels: the `footnote_labels` core rule (after `block`) normalises definition labels (`toUpperCase().toLowerCase()`, as markdown-it does for reference labels). It parks a later duplicate under an unreachable label, so the first definition wins. It also replaces `env.footnotes.refs` with a Proxy that normalises keys, so the plugin's inline `footnote_ref` lookup becomes case-insensitive.
    - `footnote_list_labels`, which runs before `footnote_tail`, normalises the list labels that `footnote_tail` uses to look up definitions.
    - The render rules emit GitHub/cmark-gfm markup with escaped ids and `encodeURIComponent` hrefs.
  - `reader_metadata` now runs after `footnote_tail`, so headings inside unused definitions never reach the outline. It reserves `footnote-label` and every `fn-`/`fnref-` id before assigning heading slugs (`# fn a` becomes `fn-a-1`).
  - `scrollToHeading` tries the raw id, then the decoded id, then either with `user-content-` stripped.
  - Copy: `svg.octicon`, `.sr-only` and `.footnote-backref` are removed, along with the space before each back-link. In plain text, refs become `[n]`, footnote items become `[n] text` (the number comes from the live list), and whitespace-only text nodes in SECTION and in footnote items are ignored. Rich HTML drops the in-document footnote anchors (leaving `<sup>n</sup>`) and gives alerts and the footnotes section portable inline styles. These are collected before classes are stripped: a first version lost the title colour because the parent's class had already been removed.
  - Find: `indexText` skips `.sr-only`.
- **CSS:** GitHub alert colours are variables for light and dark. The CSS covers alert box/title/icon, `.sr-only`, footnote reference metrics, `scroll-margin-top`, and a muted footnotes section with a top border.
- **Packaging/docs:** I updated `index.html` (loads the plugin after markdown-it), `validate-bundle.sh` (requires the plugin and both licenses), `THIRD_PARTY.md` and the README "Reading" bullets.
- **GUI** (`ReaderChecks.swift`): a new section after the front-matter checks, using its own fixture and native mouse clicks on the footnote reference and back-link. While writing it, two of my own fixture mistakes showed up: the filler text and the H1 contained "footnotes", which matches the case-insensitive find for "Footnotes". WebKit also normalises clipboard colours to `rgb()`. I fixed the fixture and the expectation; the product was not wrong.

## Outcome

Independent verification by the coordinating session: `make check` (Swift 11/11, renderer 35/35), `make gui-test` 52/52, `make validate-bundle` OK; alerts-dark snapshot inspected.


GitHub alerts (all five types, GitHub's marker rules) and GitHub-style footnotes (first-use numbering, case-insensitive labels, first duplicate wins, unused definitions hidden, back-links for repeated refs) render in the continuous WebKit page. Copy, find and the outline handle both.

Remaining differences from GitHub:
- Footnote ids omit GitHub's `user-content-` prefix and per-document hash. Links written as `#user-content-fn-x` still resolve; hashed ids do not.
- Headings inside *used* footnote definitions appear in the outline after body headings.
- Alerts inside footnote definitions are not recognised, because they are not at the top level (GitHub behaviour not fixture-checked).
